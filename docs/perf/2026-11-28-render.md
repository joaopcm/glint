# render memory, 2026-11-28

the slice 1 exporter reads raw screen frames as YUV and composites them itself. the spike (appendix of `docs/superpowers/specs/2026-11-28-native-video-editor-design.md`) peaked at 1,375 to 1,560 MB for a 6K HEVC render. this doc measures the real exporter and sets `MemoryBudget.render` from it.

| source | output | codec | seconds per 60 s | peak MB |
| --- | --- | --- | --- | --- |
| 6016x3384 | 3840x2160 (capped) | HEVC | 34.2 | 348.5 |
| 6016x3384 | 3840x2160 (capped) | H.264 | 57.8 | 357.4 |
| 6016x3384 | 6016x3384 (full size) | HEVC | 80.8 | 688.6 |
| 6016x3384 | 6016x3384 (full size) | H.264 | 405.6 | 595.7 |
| 1920x1080 | 1920x1080 | HEVC | 16.4 | 156.7 |
| 1920x1080 | 1920x1080 | H.264 | 15.6 | 155.9 |

one run per row. the cap doesn't apply at 1080p, so there is no capped row for it.

## setup

- Mac16,8 (Apple M4 Pro), 24 GB, macOS 27.2.1
- on battery: 58% discharging at the start, 51% at the end (`pmset -g batt`). the machine wasn't plugged in
- not idle: load average was 5.1 at the start and 5.5 at the end, two users logged in, normal desktop apps open
- no 6K display is attached. that doesn't matter here, the benchmark writes its own 6016x3384 source file and never draws to a screen

## method

`swift run -c release RenderBenchmark 6016x3384` and `... 1920x1080`, in `Packages/LunettaStudio/Sources/RenderBenchmark/main.swift`.

- it writes a synthetic project first: a 60 s, 60 fps HEVC screen part whose content changes every frame, a 1280x720 30 fps H.264 camera clip with the camera overlay on, and an event log with pointer motion at 60 Hz, a cursor image, a click every 2 s and a key every 3 s. the spike's generator isn't in the repo, so this is a rebuild from the appendix description, not the same file
- no audio track in either clip. audio goes through its own small pump and I expect it to add little, but it isn't in these numbers
- each case runs in its own process, re-launched by the benchmark. the numbers are that process's `ledger_phys_footprint_peak` from `task_info(TASK_VM_INFO)`, read after the export finishes. that is the peak of the whole process lifetime, not a sampled maximum
- each case goes through the real `ProjectComposition.make(project:folder:)` and `ProjectExporter.export(...)` with `MemoryBudget.unlimited`, at 60 fps. seconds is wall time for both calls
- source files are written before any case runs, in the parent process, so generating them isn't counted in a case

peak memory is about half the spike's in every row. the 4K rows aren't the same input: the spike's 4K source was a 4K clip, these are the 6K source scaled down, so the 4K comparison is loose.

time matches the spike for HEVC and for 4K H.264. 6K H.264 took 405.6 s against the spike's 222.8 s, and I don't know why. the spike also ran on battery and noted a slowdown there, and this run had a load average above 5, so a busy machine is my guess. I didn't rerun it.

## the limit

largest peak is 688.6 MB (6016x3384 full size, HEVC), under the 1,024 MB bar for the YUV pipeline.

limit = 2 x 688.6 MB = 1,377.2 MB, rounded up to 1,378 MB.

that is a tripwire: no good render gets near it, even the largest one measured is at half. if a real recording trips it, the error names the budget, the limit and the output size, and the number here gets measured again.
